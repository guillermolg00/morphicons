# Astro support is a custom element plus an SSR shell, not a framework port

Astro has no client component runtime: a `.astro` component renders once on the server and its props die there, so the lifecycle contract (lazy driver, controlled wins, clean re-entry) has nothing to attach to — the contract is defined over a reactive prop surface, and a pure `.astro` port has none. The reactive surface Astro *does* ship to the client is the platform's own: custom elements. We decided the fifth binding is `<morph-icon>` (`morphicons/element`), a custom element whose attributes, properties and methods wire into the same shared controller as the Svelte binding (extracted to `src/dom/controller.ts` for exactly this), and `morphicons/astro` is a logic-free `.astro` shell over it: it SSRs the exact initial SVG with the pure core and defines the element in one processed script per page, so hydration IS custom-element upgrade.

## Considered Options

1. **Pure `.astro` component.** SSR is trivial, but there is no post-render reactivity: the three modes cannot exist and client-side control would need an ad-hoc event/registry protocol invented here and used nowhere else. Rejected: it would be the only binding that can't honor the lifecycle contract.
2. **Islands only (document the existing bindings with `client:*`).** Works today and stays the right answer for an icon living inside an existing React/Vue/Svelte island. Rejected as the whole answer: it taxes every standalone icon with a framework runtime — the exact cost an Astro user chose to avoid.
3. **Custom element + SSR shell (chosen).** The element is per *platform*, not per framework (the same spirit as adapters per format, ADR 0001): one entry serves Astro, plain HTML, HTMX, Rails, anything server-rendered. The shell contributes exactly what Astro adds and nothing more: server-exact first paint and the per-page define.

## Consequences

- The element joins the mirrored mount suites: the lifecycle contract now spans five bindings and no fix may land in just one. Its analog of "the same update" is consecutive property assignments in program order — the element has no batching, and the mount suite documents that.
- SSR adoption is verbatim, literally: a server-rendered `<svg><path>` inside the element is adopted, never re-rendered — and never re-written. The first mount over adopted markup goes through a write-gated `PathEl` that swallows the driver's initialization writes (they only re-derive the bytes the server painted: the identical canonical `d`, or the frozen pair shape modulo last-ulp trig, the same engine-difference the 1.4.2 quantization fix chased), so upgrade performs ZERO `d` writes — pinned by instrumented-`setAttribute` tests. A pre-upgrade script mutation (property write or imperative call) disables the gate, because then the SSR bytes no longer describe the mount state and suppressing would freeze stale pixels. The adopted `d` becomes the at-rest icon when no `icon`/`from`/`to` arrived, so a script can `morphTo` away from server markup without restating the icon.
- Attributes carry strings only (`d` paths, spring preset names); `IconNode`s and custom spring objects ride properties. The shell forwards a controlled pair as attributes when BOTH endpoints are `d` strings — the element stays in controlled mode after upgrade and `progress` keeps scrubbing the server-frozen pair. Both-or-neither on purpose: forwarding half a mixed pair would make the element mount from the lone endpoint instead of adopting the frozen shape. `IconNode` pairs remain server-only: controlled mode for them means a client script assigning `from`/`to`/`progress` properties.
- Imperative calls before upgrade exit controlled mode exactly like live ones: `set`/`morphTo` on a not-yet-connected element clears the pending `from`/`to` pair and becomes the mount state — otherwise the pair would win the mount and silently discard the call.
- The `.astro` shell is logic-free like `MorphIcon.svelte` and is never typechecked or compile-tested (no `astro`/`@astrojs/compiler` in the toolchain); every line that can be wrong lives in `src/element` + `src/dom/controller.ts`, which are. Shell validation is by eye in the testbench, like the React Native binding.
- `morphicons/element` evaluates without a DOM (the class extends a lazy base): importing it from SSR code never throws; `defineMorphIcon` no-ops without `customElements`. No new peer dependency — the consumer's Astro compiles the shell, as with every `.astro` shipped as source.
- Disconnect destroys the driver; reconnect mounts a fresh controller at the rest state of the current props (mirrors unmount/remount in the framework bindings). Mid-flight state does not survive a DOM move.
